# Browser checks

Not unit tests, and not in CI. They need a real browser, a running dev server, and a real
video file — which is the point: OPFS, IndexedDB, `touch-action`, and `<video>` seeking
have no Node equivalents, so the parts most likely to break on an actual iPhone are
exactly the parts a headless unit test would have to mock away.

```bash
npm run dev                 # in one terminal
npm run e2e -w @evocut/web  # in another
```

`editor.spec.mjs` runs on an iPhone profile and drives every gesture with real touch
events (CDP `Input.dispatchTouchEvent`, not the mouse), so a missing `touch-action` fails
the run instead of passing silently: drag the playhead, cut, select, trim both edges,
extend back into raw footage, undo, delete, reload.

`review.spec.mjs` covers the refinement review and asserts on the exported EDL —
particularly that *rejected* suggestions are recorded, since those leave no other trace.

`export.spec.mjs` renders a real video and reads it back. It cuts the head off the take,
exports, then demuxes the result in a fresh element and samples pixels out of it. The
generated test clip's background colour is a known function of its own timestamp
(`hsl(t/40, …)`), so converting a sampled pixel back to a hue recovers *which moment of
the source* an output frame came from — which turns "did the export honour the edit?" into
a number rather than something you have to watch. Note that this Chromium has no H.264 or
AAC, so the run exercises the VP9/Opus fallback; a phone takes the AVC path through the
same container, timing, and frame-selection code.

`signals.spec.mjs` checks the analysis against a recording built to contain known answers.
The generated clip has two seconds of silence starting at 4s and sharp bursts at 7s and 9s,
so this asks whether the pass found *those*, not whether it produced plausible-looking
numbers. That distinction matters more here than elsewhere: an onset detector that is
subtly wrong does not fail, it produces a rationale citing a hit that was never there. It
also checks the result is cached, by reloading and confirming the second open does not pay
for the analysis again.

`refine.spec.mjs` runs the refinement pass with the Anthropic API intercepted. Everything
up to the network is real — the settings screen, the stored key, the SDK, the prompt
builder, the op parser, the dry-run validator, the review screen — and the handler records
what the browser actually sent. That request body is the point: it is the only place to
check the two claims the app makes to the user, that the model is told what the footage
sounds like and that the footage itself never leaves the device. It also covers the
no-key fallback, an op the engine rejects never reaching the review screen, and a rejected
key producing a message that names the fix.

Artifacts (screenshots, exported EDLs, the generated test clip) land in `e2e/artifacts/`,
which is gitignored. The test clip is generated by the browser on first run rather than
committed. It is built to contain known answers: a visible running clock, a background
colour that encodes its own timestamp, and an audio track with a deliberate shape.

Set `APP_URL` to point at a different server, and `CHROMIUM_PATH` if Playwright cannot
find a browser.
